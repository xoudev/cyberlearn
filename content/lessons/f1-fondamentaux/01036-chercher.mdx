Un serveur contient des centaines de milliers de fichiers, et un journal des millions de lignes. Les parcourir à l'œil est impossible. Deux questions reviennent pourtant sans cesse : **où est ce fichier ?** et **où est ce texte ?** La ligne de commande y répond avec deux outils, `find` et `grep`, parmi les plus utilisés de tout l'arsenal Unix, et avec les **jokers**, qui désignent plusieurs fichiers d'un seul motif. Combinés par un **tube**, ils répondent en une ligne à des questions qui prendraient des heures à la main. Cette leçon te les fait découvrir, puis te met en situation d'enquête.

## objectifs

À la fin de cette leçon, tu sais :

- désigner plusieurs fichiers avec les jokers `*`, `?` et `[ ]` ;
- chercher des fichiers avec `find` selon leur nom, leur type, leur taille ou leur date ;
- chercher du texte avec `grep` et ses options essentielles ;
- enchaîner deux commandes avec un tube `|` ;
- compter ce qu'on a trouvé ;
- utiliser ces outils pour une première enquête.

## pourquoi ça compte

« Où est le fichier de configuration du serveur web ? », « Quels fichiers ont été modifiés depuis hier ? », « Combien d'erreurs dans le journal ce matin ? », « Quel script contient ce mot de passe ? » Ce sont des questions quotidiennes en administration, en développement et en sécurité. Un analyste qui enquête sur une intrusion cherche les fichiers récemment modifiés et les lignes suspectes des journaux ; un auditeur cherche les mots de passe laissés en clair dans les configurations ; un attaquant fait exactement la même chose. `find` et `grep` sont leurs premiers outils.

## les jokers

Les **jokers** (*wildcards*, ou *globs*) permettent de désigner plusieurs noms de fichiers par un motif :

| Joker | Correspond à | Exemple |
| --- | --- | --- |
| `*` | n'importe quelle suite de caractères, même vide | `*.txt` : tous les fichiers en `.txt` |
| `?` | exactement un caractère | `photo?.jpg` : `photo1.jpg`, `photoA.jpg` |
| `[abc]` | un caractère parmi ceux listés | `rapport[123].txt` |
| `[0-9]` | un caractère dans un intervalle | `log-2026-0[1-6].txt` : le premier semestre |

Un point essentiel : c'est le **shell** qui remplace le motif par la liste des noms correspondants, **avant** de lancer la commande. Quand tu tapes `ls *.txt`, `ls` reçoit en réalité `ls notes.txt rapport.txt plan.txt`. C'est pour cela que les jokers fonctionnent avec toutes les commandes, et pour cela qu'un `rm *` est si dangereux : `rm` reçoit tous les noms du dossier, sans savoir qu'ils venaient d'un joker. Le réflexe de la leçon sur les fichiers s'applique à plein : `ls` d'abord avec le même motif, `rm` ensuite.

Par défaut, `*` ne correspond pas aux fichiers cachés : `ls *` ne montre pas `.bashrc`. Et si aucun fichier ne correspond au motif, la plupart des shells transmettent le motif tel quel à la commande, qui répond alors, par exemple, `ls: *.pdf: No such file or directory` : ce message signifie simplement qu'il n'y a aucun PDF ici.

## find : chercher des fichiers

`find` parcourt une arborescence et affiche les fichiers qui satisfont des critères. Sa forme : `find` suivi d'un **point de départ**, puis de **critères**.

```bash
find . -name "*.conf"            # les fichiers en .conf, à partir d'ici
find / -iname "readme*"          # sans tenir compte des majuscules
find . -type d                   # seulement les dossiers
find . -type f -size +10M        # les fichiers de plus de 10 Mio
find /var/log -mtime -1          # modifiés depuis moins d'un jour
find . -name "*.tmp" -delete     # les trouver et les supprimer
```

Les critères principaux :

| Critère | Signification |
| --- | --- |
| `-name motif` | le nom correspond au motif, en respectant la casse |
| `-iname motif` | idem, sans tenir compte des majuscules |
| `-type f`, `-type d` | un fichier, un dossier |
| `-size +10M`, `-size -1k` | plus de 10 Mio, moins de 1 Kio |
| `-mtime -7` | modifié il y a moins de 7 jours |
| `-user alice` | appartenant à alice |

Deux remarques importantes. D'abord, le motif de `-name` se met **entre guillemets** : sans eux, le shell développerait `*.conf` avant que `find` ne le voie, ce qui ne donne pas le résultat attendu. Ensuite, `-delete` et `-exec` agissent sur chaque fichier trouvé : on lance toujours la commande **sans** eux d'abord, pour voir la liste, exactement comme `ls` avant `rm`.

Chercher depuis la racine `/` parcourt tout le système : c'est long, et affiche beaucoup d'erreurs `Permission denied` pour les dossiers interdits. On limite donc le point de départ quand c'est possible, et on peut masquer ces erreurs en ajoutant `2>/dev/null`, qui envoie les messages d'erreur dans un trou noir.

## grep : chercher du texte

`grep` affiche les **lignes** d'un ou plusieurs fichiers qui contiennent un motif :

```bash
grep ECHEC journal.log           # les lignes qui contiennent ECHEC
grep -i erreur journal.log       # sans tenir compte des majuscules
grep -n admin journal.log        # avec le numéro de chaque ligne
grep -c ECHEC journal.log        # seulement le nombre de lignes trouvées
grep -v OK journal.log           # les lignes qui ne contiennent PAS OK
grep -r "password" /etc          # dans tous les fichiers d'une arborescence
```

| Option | Effet |
| --- | --- |
| `-i` | ignore la casse |
| `-n` | numérote les lignes trouvées |
| `-c` | compte au lieu d'afficher |
| `-v` | inverse : les lignes qui ne correspondent pas |
| `-r` | parcourt un dossier et ses sous-dossiers |
| `-l` | affiche seulement les noms des fichiers qui contiennent le motif |

Le motif de `grep` peut être bien plus riche qu'un simple mot : c'est une **expression régulière**, un langage pour décrire des motifs de texte (une adresse IP, une date, un numéro de carte). Le parcours Linux leur consacre une leçon ; pour l'instant, des mots simples suffisent, mis entre guillemets dès qu'ils contiennent un espace ou un caractère spécial.

## le tube : combiner

Le **tube** `|` envoie la sortie d'une commande dans l'entrée de la suivante. C'est ce qui permet de construire une réponse en assemblant de petits outils :

```bash
grep ECHEC journal.log | wc -l             # combien d'échecs ?
grep ECHEC journal.log | grep admin         # les échecs sur le compte admin
find . -name "*.log" | wc -l               # combien de journaux ?
```

<Diagram caption="Un tube : la sortie de l'un devient l'entrée de l'autre">
flowchart LR
  A["journal.log"] --> B["grep ECHEC : garde les lignes d'échec"]
  B -->|"tube"| C["grep admin : garde celles sur admin"]
  C -->|"tube"| D["wc -l : les compte"]
  D --> E["6"]
</Diagram>

Chaque outil fait une seule chose, bien, et le tube les assemble : c'est la philosophie d'Unix, qui explique en grande partie la longévité de ces commandes. La redirection `>`, vue avec les fichiers, complète le tube : `grep -c ECHEC journal.log > compte.txt` enregistre le résultat dans un fichier au lieu de l'afficher.

## trier et compter par valeur

Deux outils de plus transforment une liste de lignes en statistique : `sort`, qui trie, et `uniq -c`, qui regroupe les lignes identiques **consécutives** en les comptant. D'où l'enchaînement classique, qu'on trie avant de dédoublonner :

```bash
grep -o "ip=[0-9.]*" journal.log | sort | uniq -c | sort -rn
```

`grep -o` n'affiche que le morceau qui correspond, ici l'adresse IP de chaque ligne ; `sort` range les adresses identiques côte à côte ; `uniq -c` les compte ; le second `sort -rn` classe du plus grand nombre au plus petit. En une ligne, on obtient les adresses qui se connectent le plus, et celle d'un attaquant qui multiplie les essais saute aux yeux en tête de liste. Les analystes utilisent cette recette sur des journaux de plusieurs millions de lignes ; la voir fonctionner sur seize lignes permet d'en comprendre chaque étage.

## chercher des secrets : un classique de la sécurité

Des mots de passe, des clés d'API et des jetons traînent souvent là où ils ne devraient pas : dans un fichier de configuration lisible par tous, un script de sauvegarde, une ancienne copie `config.php.bak`, un historique de commandes. Un `grep -ri "password" .` sur un dossier de projet ou un serveur les fait apparaître en quelques secondes. Les auditeurs le font pour les trouver et les faire retirer ; les attaquants le font dès qu'ils ont un accès, pour s'étendre à d'autres comptes. Ce seul geste justifie la règle de base : **aucun secret en clair dans un fichier**, et encore moins dans un dépôt de code, où l'historique le garde même après sa suppression. Des outils spécialisés font cette recherche automatiquement avant chaque envoi de code, et le site que tu utilises en fait tourner un à chaque modification.

## les pièges

- **Oublier que le shell développe les jokers.** `rm *` reçoit tous les noms ; `ls` d'abord.
- **Ne pas mettre le motif de `find -name` entre guillemets.** Le shell le développerait avant `find`.
- **Lancer `find -delete` ou `-exec` sans avoir vu la liste.** On cherche d'abord, on agit ensuite.
- **Oublier la casse avec `grep`.** `-i` quand elle n'a pas d'importance.
- **Chercher depuis `/` sans raison.** C'est long et bruyant ; on part du bon dossier.
- **Laisser un secret dans un fichier.** Un simple `grep -r` suffit à le trouver.

## à retenir

- Jokers : `*` (n'importe quoi), `?` (un caractère), `[abc]`, `[0-9]`. C'est le **shell** qui les développe.
- `find départ critères` : `-name`, `-iname`, `-type f|d`, `-size`, `-mtime`, `-user`. Motifs **entre guillemets** ; `-delete` et `-exec` seulement après avoir vu la liste.
- `grep motif fichiers` : `-i`, `-n`, `-c`, `-v`, `-r`, `-l`.
- Le **tube** `|` enchaîne des outils simples ; la redirection `>` enregistre le résultat.
- `grep -r` débusque les **secrets** en clair : aucun ne doit traîner dans un fichier.
