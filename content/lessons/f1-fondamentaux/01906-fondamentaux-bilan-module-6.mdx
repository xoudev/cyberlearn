Il y a sept leçons, tu n'avais jamais écrit une ligne de Python. Tu sais maintenant décrire un algorithme, manipuler des variables et des types, faire décider un programme, le faire répéter, le découper en fonctions, le déboguer, et estimer son coût. C'est exactement la boîte à outils avec laquelle les programmeurs écrivent leurs premiers jeux depuis des décennies. Ce bilan vérifie chaque notion, puis te fait construire deux jeux classiques, le nombre mystère et le pendu, à la manière d'un professionnel : pièce par pièce, chaque pièce vérifiée par des tests automatiques avant de passer à la suivante.

## objectifs

Ce bilan valide que tu sais :

- décomposer un problème en fonctions courtes, chacune avec une responsabilité ;
- écrire des conditions et des boucles correctes, bornes comprises ;
- faire passer une série de tests automatiques, cas limites compris ;
- réutiliser une fonction dans une autre ;
- appliquer la recherche dichotomique à un problème concret ;
- lire un test qui échoue pour trouver le bug qu'il révèle.

## projet

### l'énoncé

Tu vas programmer deux jeux. Le **nombre mystère** : l'ordinateur choisit un nombre entre 1 et n, le joueur propose des nombres, et l'ordinateur répond « plus grand », « plus petit » ou « gagné ». Puis le **pendu** : un mot est caché, le joueur propose des lettres, les lettres trouvées se dévoilent, et chaque lettre absente du mot rapproche le joueur de la défaite.

Comme dans un vrai projet, tu ne vas pas écrire un gros programme d'un seul bloc. Chaque jeu est découpé en **fonctions pures**, qui reçoivent tout par leurs paramètres et renvoient leur résultat, et chaque fonction est vérifiée par des **tests automatiques** avant qu'on passe à la suivante. C'est la méthode des leçons 1 et 5 du module : décomposer, puis tester chaque morceau.

<Diagram caption="Le découpage du projet">
flowchart TD
  A["Nombre mystère"] --> B["indice : compare une proposition au secret"]
  B --> C["partie : rejoue une liste de propositions"]
  B --> D["joueur_auto : gagne par dichotomie"]
  E["Pendu"] --> F["masquer : montre les lettres trouvées"]
  F --> G["etat : gagné, perdu ou en cours"]
</Diagram>

Une remarque sur les entrées. Un vrai jeu lit les propositions au clavier avec `input`. Les tests automatiques, eux, ne peuvent pas taper au clavier : c'est pourquoi les fonctions reçoivent les propositions en **paramètre**, sous forme de liste. Séparer la **logique** du jeu de la **saisie** est une excellente habitude : c'est ce qui rend la logique testable. À la fin, tu verras comment brancher un clavier sur ces fonctions.

Pour chaque étape : écris d'abord le pseudo-code, trace-le sur un exemple, puis code, et lance les tests. Quand un test échoue, lis son libellé : il te dit quel cas tu as oublié.

### étape 3 : un joueur qui gagne toujours

Maintenant, fais jouer l'ordinateur contre lui-même. `solution(secret, n)` simule un joueur qui cherche un secret entre 1 et n par **dichotomie** : il propose le milieu de l'intervalle encore possible, calculé avec `(bas + haut) // 2`, réduit l'intervalle selon l'indice, et recommence. La fonction renvoie le nombre d'essais. D'après la leçon sur l'efficacité, il ne devrait jamais dépasser dix essais entre 1 et 1 000 : le dernier test le vérifie sur les mille secrets possibles.

### brancher le clavier

Tes fonctions sont testées : il ne reste qu'à les relier à un vrai joueur. Avec Python installé sur ta machine, ou dans la machine virtuelle Debian du module 3, enregistre ceci dans un fichier `mystere.py` à côté de tes fonctions, puis lance `python3 mystere.py` dans un terminal :

```python
import random

secret = random.randint(1, 100)
essais = 0
while True:
    texte = input("Ta proposition entre 1 et 100 : ")
    if not texte.isdigit():
        print("Il faut un nombre entier positif.")
        continue
    essais += 1
    reponse = indice(secret, int(texte))
    print(reponse)
    if reponse == "gagné":
        print("Trouvé en", essais, "essais")
        break
```

Remarque la vérification de la saisie avant la conversion : c'est la leçon sur les types. Sans elle, le premier joueur qui tape `abc` fait planter le jeu avec une `ValueError`. La logique, déjà testée, n'a pas eu à changer : seule la saisie est nouvelle.

### la correction commentée

Ne lis cette partie qu'après avoir essayé : c'est en cherchant qu'on apprend. Voici les deux étapes les plus délicates.

```python
def partie(secret, propositions):
    essais = 0
    for proposition in propositions:
        essais += 1
        if indice(secret, proposition) == "gagné":
            return essais          # on sort dès la victoire
    return -1                      # la boucle s'est terminée sans victoire
```

Le `return` à l'intérieur de la boucle règle d'un coup le cas des propositions après la victoire : la fonction s'arrête au premier « gagné ». Le `return -1` après la boucle ne s'exécute que si aucune proposition n'a gagné, liste vide comprise.

```python
def joueur_auto(secret, n):
    bas, haut = 1, n
    essais = 0
    while bas <= haut:
        milieu = (bas + haut) // 2
        essais += 1
        reponse = indice(secret, milieu)
        if reponse == "gagné":
            return essais
        elif reponse == "plus grand":
            bas = milieu + 1       # le secret est au-dessus du milieu
        else:
            haut = milieu - 1      # le secret est en dessous
    return essais
```

C'est la recherche dichotomique de la leçon 7, où la comparaison avec la liste est remplacée par l'indice du jeu. L'intervalle rétrécit d'au moins un élément à chaque tour, donc la boucle termine ; et il est divisé par deux, donc dix essais suffisent pour mille nombres.

Pour `etat`, l'ordre des tests compte. Un mot trouvé est gagné même si le joueur a fait des erreurs en chemin ; on teste donc `trouve` avant `erreurs`. Et pour compter les erreurs distinctes, on parcourt les lettres proposées en ignorant celles déjà comptées, par exemple en les ajoutant à un texte `deja_vues` : c'est le motif du filtre, avec un test d'appartenance.

### pour aller plus loin

Améliore le jeu, une fonction à la fois, avec ses tests : limiter le nombre d'essais du nombre mystère, afficher le dessin du pendu selon le nombre d'erreurs, choisir le mot au hasard dans une liste, refuser une lettre déjà proposée. Puis pose-toi une question d'efficacité : si le pendu devait deviner un mot parmi les trois cent mille mots d'un dictionnaire, quelle lettre proposer en premier pour éliminer le plus de mots possible ? C'est, en miniature, le raisonnement des outils qui cassent les mots de passe en essayant d'abord les plus probables.

## à retenir

- Un projet se construit **pièce par pièce** : une fonction, ses tests, puis la suivante.
- Des **fonctions pures**, sans saisie ni affichage, se testent automatiquement ; la **saisie** se branche à la fin.
- Réutiliser une fonction testée (`indice` dans `partie` et `joueur_auto`) évite de réécrire, et de réintroduire des bugs.
- La **dichotomie** garantit au plus dix essais pour mille nombres, parce que l'intervalle est divisé par deux à chaque tour.
- Un test qui échoue n'est pas un échec : son libellé indique le **cas oublié**.
- Toute saisie est **vérifiée** avant d'être convertie.
