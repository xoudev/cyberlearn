Personne ne tape `151.101.2.132` pour mettre à jour un serveur : on tape `deb.debian.org`. Entre les deux, une chaîne de mécanismes transforme le nom en adresse, en consultant d'abord des fichiers locaux, puis des serveurs DNS. Quand cette chaîne casse, tout semble en panne alors que le réseau fonctionne parfaitement, comme l'a montré la leçon précédente. Et quand elle est détournée, une machine peut envoyer ses mots de passe à un faux serveur sans que rien ne paraisse anormal. Cette leçon te montre chaque maillon, et comment l'interroger.

## objectifs

À la fin de cette leçon, tu sais :

- régler le nom d'une machine, et ce que signifie son nom complet ;
- décrire la chaîne de résolution : `nsswitch`, `/etc/hosts`, `/etc/resolv.conf` ;
- utiliser `/etc/hosts` à bon escient, et savoir qui l'emporte ;
- lire la configuration de `systemd-resolved` avec `resolvectl` ;
- reconnaître les enregistrements DNS courants, et les interroger avec `dig` ;
- repérer les attaques qui visent la résolution des noms.

## pourquoi ça compte

La résolution des noms est un point de confiance : la machine croit ce qu'on lui répond. Un attaquant qui modifie `/etc/hosts` peut faire pointer le nom de la banque, du dépôt de paquets ou de l'annuaire de l'entreprise vers son propre serveur. Un résolveur DNS compromis peut le faire pour tout un réseau. À l'inverse, les requêtes DNS d'une machine en disent long sur ce qu'elle fait, et un logiciel malveillant qui fait sortir des données dans des requêtes DNS laisse des traces que seule une équipe attentive remarque. Comprendre la chaîne, c'est savoir où regarder.

## le nom de la machine

```bash
hostnamectl                                 # le nom, le système, le noyau
sudo hostnamectl set-hostname srv-web       # changer le nom, de façon permanente
hostname -f                                 # le nom complet (FQDN), avec le domaine
```

Le nom court, `srv-web`, est rangé dans `/etc/hostname`, lu au démarrage. Le nom **complet** (*FQDN*, *fully qualified domain name*) y ajoute le domaine : `srv-web.labo.example`. Sur Debian, une convention ajoute dans `/etc/hosts` une ligne qui fait pointer le nom de la machine vers `127.0.1.1`, pour qu'elle se trouve toujours elle-même, même sans réseau ni DNS. Changer le nom avec `hostnamectl` met à jour `/etc/hostname`, mais pas cette ligne : on la corrige à la main, sous peine d'avertissements de `sudo` (`unable to resolve host`).

## la chaîne de résolution

Quand un programme demande l'adresse d'un nom, la bibliothèque C consulte **`/etc/nsswitch.conf`**, qui dit quelles sources interroger, et dans quel ordre :

```text
hosts:          files dns
```

`files` désigne **`/etc/hosts`**, consulté en premier ; `dns` les serveurs de **`/etc/resolv.conf`**, interrogés seulement si le fichier n'a rien donné. Certaines distributions ajoutent d'autres sources, comme `mdns4_minimal` pour les noms `.local` du réseau local, ou `myhostname` pour que la machine se résolve toujours elle-même.

**`/etc/hosts`** associe des adresses à des noms, une ligne par adresse :

```text
127.0.0.1    localhost
127.0.1.1    srv-web.labo.example srv-web
192.0.2.20   srv-base.labo.example srv-base
```

Il ne passe pas par le réseau, ne connaît pas de délai, et l'emporte sur le DNS. On s'en sert pour tester un site avant d'en changer l'enregistrement DNS, ou pour qu'une machine trouve ses voisines même si le DNS tombe. Mais chaque nom qu'on y met est un nom de plus à maintenir à la main, sur chaque machine : au-delà de quelques entrées, c'est le travail du DNS. Quand un nom figure deux fois, c'est la **première** ligne qui gagne.

**`/etc/resolv.conf`** désigne les serveurs DNS :

```text
nameserver 192.0.2.53
nameserver 192.0.2.54
search labo.example
```

Les `nameserver` sont interrogés dans l'ordre, le second seulement si le premier ne répond pas. `search` ajoute un domaine aux noms courts : `ping srv-base` essaie aussi `srv-base.labo.example`. Ce fichier est souvent **généré** par NetworkManager, systemd-resolved ou le client DHCP : une modification à la main peut être écrasée au prochain renouvellement. On règle alors les serveurs DNS dans l'outil qui le génère.

## systemd-resolved

Sur Ubuntu, Fedora et de plus en plus de distributions, **systemd-resolved** sert d'intermédiaire : `/etc/resolv.conf` y pointe vers un résolveur local, `127.0.0.53`, qui garde les réponses en cache et choisit les vrais serveurs DNS selon l'interface.

```bash
resolvectl status                       # les serveurs DNS de chaque interface
resolvectl query deb.debian.org         # résoudre, en montrant d'où vient la réponse
resolvectl flush-caches                 # vider le cache
```

Si `cat /etc/resolv.conf` ne montre que `nameserver 127.0.0.53`, c'est `resolvectl status` qui dit quels serveurs sont vraiment utilisés. systemd-resolved sait aussi chiffrer les requêtes vers les serveurs qui le permettent (DNS sur TLS), et valider les signatures DNSSEC.

## les enregistrements DNS

Le DNS ne contient pas que des adresses. Les types d'enregistrement qu'un administrateur rencontre :

| Type | Contenu | Exemple |
| --- | --- | --- |
| `A` | une adresse IPv4 | `srv-web.labo.example → 192.0.2.10` |
| `AAAA` | une adresse IPv6 | `→ 2001:db8::10` |
| `CNAME` | un alias vers un autre nom | `www.labo.example → srv-web.labo.example` |
| `MX` | le serveur de messagerie d'un domaine | `labo.example → 10 mail.labo.example` |
| `TXT` | du texte, dont les règles SPF et DKIM de la messagerie | `"v=spf1 mx -all"` |
| `PTR` | le nom d'une adresse : la résolution inverse | `192.0.2.10 → srv-web.labo.example` |
| `NS`, `SOA` | les serveurs qui font autorité pour le domaine | |

Chaque réponse porte une **durée de vie** (*TTL*) : le temps pendant lequel les résolveurs la gardent en cache. Changer l'adresse d'un site dont le TTL est d'un jour, c'est accepter que certains visiteurs arrivent à l'ancienne adresse pendant un jour. Avant une migration, on baisse donc le TTL quelques jours à l'avance.

```bash
dig srv-web.labo.example              # l'enregistrement A, avec son TTL
dig AAAA srv-web.labo.example
dig MX labo.example
dig -x 192.0.2.10                     # la résolution inverse
dig +trace deb.debian.org             # suivre la délégation depuis la racine
```

## les attaques sur la résolution

- **Un `/etc/hosts` détourné** : un logiciel malveillant y ajoute `203.0.113.66 banque.example` ou fait pointer le serveur de mises à jour d'un antivirus vers une adresse morte. On surveille ce fichier, et un outil d'intégrité, comme AIDE, signale toute modification.
- **L'empoisonnement du cache** : de fausses réponses injectées dans un résolveur, qui les sert ensuite à tout le réseau. **DNSSEC** signe les enregistrements, pour qu'un résolveur qui valide rejette une réponse falsifiée.
- **L'écoute et la falsification sur le réseau local** : les requêtes DNS classiques circulent en clair, sans authentification. Le DNS sur TLS ou HTTPS les chiffre.
- **Le DNS comme canal de sortie** : des données découpées dans des noms comme `a3f9c2.exfil.attaquant.example`, que le résolveur transmet docilement. Journaliser les requêtes DNS, et repérer des volumes ou des noms anormaux, fait partie de la surveillance d'un réseau.

## les caches, et pourquoi un changement tarde

Une réponse DNS est gardée en cache à plusieurs endroits : par le résolveur de l'entreprise, par systemd-resolved sur la machine, parfois par le navigateur ou par l'application elle-même. Quand un enregistrement vient de changer, ces caches continuent de servir l'ancienne valeur jusqu'à l'expiration de son TTL. Pour vérifier la nouvelle valeur à la source, on interroge directement un serveur qui fait autorité : `dig @ns1.labo.example www.labo.example`. Pour vider le cache local : `sudo resolvectl flush-caches`. Les réponses **négatives** se mettent aussi en cache : un nom demandé une minute avant sa création peut rester « inexistant » pendant la durée fixée par l'enregistrement `SOA` du domaine.

## démonstration : un nom qui résout mal

Après la migration de la base de données vers `192.0.2.21`, une application continue de joindre l'ancienne adresse. `dig +short srv-base.labo.example` donne bien `192.0.2.21` : le DNS est à jour. Mais `getent hosts srv-base` répond `192.0.2.20` : la vraie chaîne de résolution trouve autre chose. Un `grep srv-base /etc/hosts` révèle la coupable, une ligne ajoutée deux ans plus tôt pour un test, et jamais retirée. On la supprime, et `getent` donne enfin la bonne adresse. Le réflexe à retenir : quand `dig` et le système ne sont pas d'accord, regarder `/etc/hosts` en premier.

## à toi de jouer

Le Linux des exercices n'a ni DNS ni réseau. Il a pourtant une chaîne de résolution, que tu vas observer :

1. son nom : `hostname`. Il répond `(none)` : aucun script de démarrage n'a appliqué de nom. `cat /etc/hostname` montre celui qui était prévu, `buildroot`, le nom par défaut de l'outil qui a fabriqué ce système ;
2. renomme la machine : `echo srv-labo > /etc/hostname`, applique avec `hostname -F /etc/hostname`, puis vérifie et garde le résultat : `hostname > nom.txt` ;

4. ajoute le serveur de base de données de l'équipe : `printf '192.0.2.20 srv-base.labo.example srv-base\n' >> /etc/hosts` ;
5. demande à `wget` de joindre ce nom, et garde ce qu'il affiche : `wget http://srv-base/ 2> resolution.txt`, puis `cat resolution.txt`. La connexion échoue, faute de réseau, mais la ligne `Connecting to` montre l'adresse trouvée ;

8. garde une copie du fichier final : `cp /etc/hosts hosts.txt`.

## les pièges

- **Changer le nom d'une machine sans corriger `/etc/hosts`.** `sudo` se plaint, et certains services ne démarrent plus.
- **Modifier `/etc/resolv.conf` à la main quand un outil le génère.** La modification disparaît au prochain renouvellement.
- **Une vieille entrée dans `/etc/hosts`.** Elle l'emporte sur le DNS, en silence.
- **Changer une adresse avec un TTL long.** Des visiteurs arrivent à l'ancienne adresse pendant toute sa durée : baisser le TTL avant.
- **Se fier à `dig` pour savoir comment le système résout.** `dig` interroge le DNS seul ; `getent hosts` suit la vraie chaîne, `/etc/hosts` compris.
- **Ne pas surveiller `/etc/hosts`.** C'est une cible discrète pour détourner le trafic.

## à retenir

- Le nom : **`hostnamectl set-hostname`**, dans `/etc/hostname`, et la ligne **`127.0.1.1`** de `/etc/hosts` à tenir à jour.
- La chaîne : **`/etc/nsswitch.conf`** (`files dns`), **`/etc/hosts`** en premier (la première ligne gagne), puis les serveurs de **`/etc/resolv.conf`**.
- **systemd-resolved** : `127.0.0.53`, et **`resolvectl status`** pour les vrais serveurs.
- Enregistrements : **A**, **AAAA**, **CNAME**, **MX**, **TXT**, **PTR** ; un **TTL** à baisser avant un changement.
- **`dig`** interroge le DNS ; **`getent hosts`** résout comme le système.
- Attaques : `/etc/hosts` détourné, cache empoisonné (**DNSSEC**), écoute (**DNS chiffré**), exfiltration par DNS.
