Depuis le début du parcours, tu tapes tes commandes une par une. C'est parfait pour explorer, mais un administrateur refait sans cesse les mêmes gestes : vérifier l'espace disque, archiver des journaux, créer un compte avec les bons réglages, préparer un serveur. Le jour où une suite de commandes revient pour la troisième fois, on l'écrit dans un **script** : un fichier texte qui contient des commandes, que le shell exécute de haut en bas. Ce module t'apprend à écrire des scripts Bash fiables, du premier fichier de trois lignes jusqu'au script de sauvegarde planifié qui tourne seul chaque nuit.

## objectifs

À la fin de cette leçon, tu sais :

- écrire un script et choisir son interpréteur avec la ligne **shebang** ;
- rendre un script exécutable, et le lancer de plusieurs façons en sachant ce qui les distingue ;
- lire les **arguments** passés au script : `$0`, `$1`, `$#`, `"$@"` ;
- terminer un script avec un **code de retour** qui dit s'il a réussi ;
- donner à un script un en-tête qui explique à quoi il sert et comment l'appeler.

## pourquoi ça compte

Un script, c'est d'abord de la **mémoire** : la procédure exacte, sans l'étape oubliée à 2 h du matin. C'est aussi de la **reproductibilité** : la même opération, faite de la même façon sur dix serveurs. Mais c'est du code qui tourne souvent avec les droits de root, parfois sans personne pour le surveiller. Un script mal écrit peut supprimer les mauvais fichiers, annoncer une sauvegarde réussie qui n'a jamais eu lieu, ou ouvrir une faille : un script appelé par une tâche planifiée et modifiable par n'importe qui est une porte d'entrée classique pour passer root. Écrire des scripts, c'est donc apprendre à les écrire **proprement** dès le premier.

## un script, c'est un fichier de commandes

Voici un script complet :

```bash
#!/bin/bash
# espace.sh : affiche l'espace disque et les plus gros dossiers de /var.
echo "Espace disque :"
df -h /
echo
echo "Les cinq plus gros dossiers de /var :"
du -sh /var/* 2>/dev/null | sort -h | tail -5
```

Rien de nouveau dans les commandes : ce sont celles que tu connais. Le shell lit le fichier ligne par ligne et exécute chaque commande comme si tu l'avais tapée. Ce qui commence par `#` est un **commentaire**, ignoré à l'exécution, sauf la toute première ligne, qui joue un rôle à part.

## le shebang : quel interpréteur ?

La première ligne, `#!/bin/bash`, s'appelle le **shebang** (de *hash*, le `#`, et *bang*, le `!`). Quand tu exécutes le fichier, c'est le **noyau** qui la lit : il lance le programme indiqué en lui passant le chemin du script. `#!/bin/bash` dit donc « fais lire ce fichier par bash ». Les variantes courantes :

| Shebang | Effet |
| --- | --- |
| `#!/bin/bash` | Bash, à l'emplacement standard. Le choix de ce module |
| `#!/usr/bin/env bash` | Le premier `bash` trouvé dans le `PATH` : utile quand bash n'est pas dans `/bin`, comme sur certains BSD ou sur macOS avec un bash récent |
| `#!/bin/sh` | Le shell POSIX du système : `dash` sur Debian et Ubuntu, `ash` sur Alpine ou BusyBox. Plus portable, mais sans les ajouts de bash |
| `#!/usr/bin/python3` | Le même mécanisme vaut pour tout interpréteur |

Le piège classique : écrire `#!/bin/sh` puis utiliser des fonctions propres à bash, comme les tableaux ou `[[ ]]`. Le script marche sur ta machine, où `sh` est peut-être bash, et casse sur une Debian, où `sh` est `dash`. Règle simple : **si tu écris du bash, déclare bash**. Le shebang doit être **la toute première ligne**, sans espace ni ligne vide avant.

## rendre un script exécutable

Un fichier qu'on vient de créer n'a pas le droit d'exécution. Tu l'ajoutes avec `chmod`, vu au module 4 :

```bash
chmod 755 espace.sh    # rwxr-xr-x : tout le monde lit et exécute, seul le propriétaire modifie
chmod u+x espace.sh    # ajoute seulement l'exécution pour le propriétaire
```

Pour un script d'administration, la règle d'or est que **personne d'autre que son propriétaire ne puisse le modifier**. Un script lancé par root, mais modifiable par un autre compte, permet à ce compte de faire exécuter n'importe quoi à root. `755` ou `700` conviennent ; `777` ne convient jamais.

## lancer un script : quatre façons

```bash
./espace.sh            # exécute le fichier : il faut le droit x, et le shebang choisit l'interpréteur
bash espace.sh         # lance bash en lui donnant le fichier à lire : pas besoin du droit x
sh espace.sh           # même chose avec sh : le shebang est ignoré !
source espace.sh       # exécute le fichier dans le shell courant (aussi : . espace.sh)
```

Le `./` est nécessaire parce que le répertoire courant n'est **pas** dans le `PATH` : c'est voulu, pour qu'un fichier piégé nommé `ls`, déposé dans un dossier, ne soit pas lancé à ta place. Pour appeler un script par son seul nom, on le range dans un dossier du `PATH`, comme `/usr/local/bin` pour tout le système ou `~/.local/bin` pour ton compte.

Les trois premières façons lancent un **nouveau processus** : le script a sa propre copie des variables, et ce qu'il change (un `cd`, une variable) disparaît quand il se termine. `source` fait l'inverse : les commandes s'exécutent dans **ton** shell, et leurs effets restent. C'est ce qu'on veut pour charger des réglages ou une bibliothèque de fonctions, et c'est ce que fait ton shell avec `~/.bashrc` à chaque ouverture. Un `exit` dans un fichier chargé par `source` ferme donc ton propre terminal.

## les arguments

Ce qu'on écrit après le nom du script lui est transmis sous forme d'**arguments**, que le script lit dans des variables spéciales :

| Variable | Contenu |
| --- | --- |
| `$0` | le nom du script, tel qu'il a été appelé |
| `$1`, `$2`… `$9` | le premier, le deuxième… le neuvième argument |
| `${10}` | le dixième : au-delà de 9, les accolades sont obligatoires |
| `$#` | le nombre d'arguments |
| `"$@"` | tous les arguments, chacun gardé intact |
| `$*` | tous les arguments, collés en une seule chaîne |

```bash
#!/bin/bash
# copier.sh : copie un fichier dans le dossier de sauvegarde.
echo "Le script $0 a reçu $# argument(s)."
cp "$1" /srv/sauvegardes/
```

`./copier.sh "rapport final.pdf"` donne **un** argument, grâce aux guillemets : `$1` vaut `rapport final.pdf`. Sans guillemets, le shell aurait découpé le nom en deux arguments. Et dans le script, les guillemets autour de `"$1"` sont tout aussi indispensables, pour la même raison : on y reviendra longuement à la leçon suivante. Pour transmettre tous les arguments à une autre commande sans rien abîmer, on écrit toujours `"$@"`, entre guillemets.

La commande intégrée `shift` décale les arguments : `$2` devient `$1`, `$3` devient `$2`, et `$#` diminue de un. On s'en sert pour traiter les arguments un par un, ce que tu feras avec les boucles et les options.

## le code de retour

Chaque commande se termine par un **code de retour**, un nombre de 0 à 255 : **0** veut dire succès, tout le reste veut dire échec. La variable `$?` contient le code de la dernière commande :

```bash
ls /etc/passwd ; echo $?     # 0
ls /nexistepas ; echo $?     # 2 : ls a échoué
```

Un script fait de même avec `exit` : `exit 0` pour dire « tout s'est bien passé », `exit 1` ou un autre nombre pour signaler un problème. Sans `exit`, le script rend le code de **sa dernière commande**, ce qui peut cacher un échec survenu plus haut. Ce code n'est pas un détail : c'est lui que lisent les tâches planifiées, les outils de supervision et les autres scripts pour décider de la suite. Un script de sauvegarde qui échoue en rendant 0 est pire qu'un script qui n'existe pas, parce que tout le monde le croit en bonne santé. La leçon sur les conditions apprend à exploiter ces codes, celle sur la robustesse à ne jamais les perdre.

## un en-tête qui sert

Un script se relit bien plus souvent qu'il ne s'écrit, souvent par quelqu'un d'autre, souvent pendant un incident. Quelques lignes en tête suffisent :

```bash
#!/bin/bash
# purge-cache.sh : supprime les fichiers de cache de plus de 7 jours.
# Usage : purge-cache.sh DOSSIER
# Codes de retour : 0 succès, 1 erreur, 2 mauvais usage.
# Planifié chaque nuit à 3 h (crontab de root).
```

Ce que fait le script, comment l'appeler, ce que veulent dire ses codes de retour, et d'où il est lancé : de quoi comprendre en vingt secondes ce que fait ce fichier trouvé dans `/usr/local/bin`. Donne aussi au fichier un **nom qui dit ce qu'il fait** : `purge-cache.sh`, pas `script2.sh`. L'extension `.sh` n'a aucun effet pour le système, c'est le shebang qui compte, mais elle aide les humains et les éditeurs.

## à toi de jouer

Le terminal ci-dessous démarre dans le shell de BusyBox, `ash`. Les scripts que tu vas lancer, eux, déclarent bash dans leur shebang : c'est bash qui les exécutera, sans que tu aies à le choisir. Le dossier de travail contient `arguments.sh`, qui montre ce qu'un script reçoit.

1. lis-le avec `cat arguments.sh`, puis lance-le avec `./arguments.sh` : le système refuse, il manque le droit d'exécution ;
2. donne-le-lui avec `chmod 755 arguments.sh`, puis relance-le ;
3. appelle-le avec deux arguments, dont un nom qui contient une espace, et garde le résultat : `./arguments.sh "rapport final.txt" notes.txt > args.txt`, puis `cat args.txt` ;
4. lance-le maintenant avec `sh arguments.sh` : la ligne de l'interpréteur reste vide, car `sh` a ignoré le shebang ;
5. écris ton premier script, `salut.sh`, avec un here-document (tape les lignes une à une, `FIN` termine le texte) :

```bash
cat > salut.sh << 'FIN'
#!/bin/bash
# salut.sh : salue la personne dont le nom est passé en argument.
echo "Bonjour, $1 !"
echo "Tu m'as donné $# argument(s)."
FIN
```

6. rends-le exécutable avec `chmod 755 salut.sh`, puis lance-le en gardant sa sortie : `./salut.sh Alice > salut.txt`.

Remarque le résultat de l'étape 3 : `Nombre d'arguments : 2`, et le premier argument garde son espace. Sans les guillemets autour de `"rapport final.txt"`, le script en aurait reçu trois. ## les pièges

- **Oublier le shebang, ou le mettre après une ligne vide.** Le script est alors lu par le shell qui le lance, pas forcément bash.
- **Écrire `#!/bin/sh` et utiliser du bash.** Ça marche là où `sh` est bash, et casse sur Debian, où `sh` est `dash`.
- **Taper `script.sh` au lieu de `./script.sh`.** Le dossier courant n'est pas dans le `PATH` : « commande introuvable ».
- **Rendre un script d'administration modifiable par tous.** Un `chmod 777` sur un script lancé par root offre root à n'importe quel compte.
- **Lancer avec `source` un script qui fait `exit`.** C'est ton propre shell qui se ferme.
- **Utiliser `$1` sans guillemets.** Un nom de fichier avec une espace devient deux arguments.
- **Écrire des fins de ligne Windows.** Un script édité sous Windows et copié tel quel échoue avec `bad interpreter: /bin/bash^M` : `dos2unix` le répare.

## à retenir

- Un **script** est un fichier de commandes. Sa première ligne, le **shebang** (`#!/bin/bash`), choisit l'interpréteur : si tu écris du bash, déclare bash.
- **`chmod 755`** le rend exécutable ; seul son propriétaire doit pouvoir le modifier.
- **`./script.sh`** l'exécute dans un nouveau processus, **`bash script.sh`** aussi sans exiger le droit `x`, **`source`** l'exécute dans ton shell.
- Les arguments : **`$1`**, **`$2`**… **`$#`** pour leur nombre, **`"$@"`** pour tous, intacts. Toujours entre guillemets.
- **`exit 0`** pour le succès, un autre code pour l'échec : c'est ce que lisent les tâches planifiées et la supervision.
- Un **en-tête** : ce que fait le script, son usage, ses codes de retour, d'où il est lancé.
