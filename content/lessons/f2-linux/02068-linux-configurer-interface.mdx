Un serveur Linux ne sert à presque rien sans le réseau : c'est par lui qu'il rend ses services, reçoit ses mises à jour, envoie ses journaux et se laisse administrer. Le parcours Réseaux t'a appris comment fonctionnent les adresses, les masques et les routes. Ce module t'apprend à les régler **sur une machine Linux** : configurer une interface, diagnostiquer une panne, faire résoudre les noms, administrer à distance par SSH, transférer des fichiers, et fermer tout ce qui ne doit pas être ouvert avec un pare-feu. Premier geste : donner une adresse à une interface, et savoir où va le trafic.

## objectifs

À la fin de cette leçon, tu sais :

- reconnaître les interfaces réseau et leurs noms ;
- lire et régler l'état d'un lien, ses adresses et ses routes avec `ip` ;
- expliquer la route par défaut et la décision de routage, avec `ip route get` ;
- distinguer une configuration temporaire d'une configuration permanente ;
- poser une adresse fixe avec NetworkManager, et reconnaître les autres outils ;
- vérifier une configuration après chaque changement.

## pourquoi ça compte

Une erreur de configuration réseau sur un serveur distant a une conséquence immédiate : on perd la main dessus. Une passerelle mal tapée, une adresse en double, un masque faux, et la session SSH se fige. Il faut alors une console, physique ou chez l'hébergeur, et parfois un déplacement. D'où deux réflexes que cette leçon installe : distinguer ce qui est temporaire de ce qui survivra au redémarrage, et toujours prévoir un moyen de revenir en arrière avant de toucher au réseau d'une machine à distance.

## les interfaces et leurs noms

```bash
ip link            # les interfaces et l'état de leur lien
ip -br link        # la même chose, une ligne par interface
```

Chaque carte réseau, physique ou virtuelle, est une **interface**. `lo`, la **boucle locale**, est toujours là : elle permet à la machine de se parler à elle-même, par l'adresse `127.0.0.1`. Les autres portent des noms **prévisibles**, construits d'après leur emplacement matériel : `enp1s0` (Ethernet, bus PCI 1, emplacement 0), `eno1` (carte intégrée à la carte mère), `wlp2s0` (Wi-Fi). Les anciens noms `eth0`, `eth1`, attribués dans l'ordre de détection, pouvaient changer d'un démarrage à l'autre, exactement comme les noms de disques : sur un pare-feu, cela pouvait inverser l'interface interne et l'interface externe. On les retrouve encore dans les machines virtuelles minimales et les conteneurs.

L'état du lien se lit entre chevrons : `UP` (l'interface est activée par le système), `LOWER_UP` (un câble ou un signal est bien détecté), `NO-CARRIER` (activée, mais rien au bout du câble).

## adresses et routes avec ip

La commande **`ip`** remplace les anciennes `ifconfig` et `route`, que l'on croise encore dans de vieux tutoriels :

```bash
sudo ip link set enp1s0 up                       # activer l'interface
sudo ip addr add 192.0.2.10/24 dev enp1s0        # lui donner une adresse, avec son masque
sudo ip route add default via 192.0.2.1          # la route par défaut, vers la passerelle
ip -br addr                                      # les adresses, une ligne par interface
ip route                                         # la table de routage
```

L'adresse se donne toujours **avec son masque**, en notation CIDR : `/24` veut dire 255.255.255.0. En l'ajoutant, le noyau crée aussi tout seul la route vers le réseau local, `192.0.2.0/24`, joignable directement par cette interface. Pour tout le reste, il lui faut une **route par défaut** : l'adresse de la **passerelle**, le routeur qui sait aller plus loin. Une interface peut porter plusieurs adresses, IPv4 comme IPv6.

## la décision de routage

Pour chaque paquet, le noyau choisit la route **la plus précise** qui correspond à la destination. `ip route get` montre ce choix, pour une adresse donnée :

```bash
ip route get 192.0.2.25       # sur le réseau local : directement, par l'interface
ip route get 198.51.100.7     # ailleurs : via la passerelle
```

C'est l'outil le plus direct pour répondre à « par où part ce trafic ? », et donc pour comprendre pourquoi un serveur joint certaines adresses et pas d'autres : une route plus précise, ajoutée un jour pour un réseau particulier, peut détourner un trafic qu'on croyait envoyé à la passerelle.

## temporaire ou permanent

Tout ce que fait `ip` est **temporaire** : la configuration disparaît au redémarrage, ou dès qu'un gestionnaire de réseau reprend la main sur l'interface. C'est parfait pour essayer ou dépanner. Pour une configuration **permanente**, chaque famille de distributions a son outil :

| Outil | Où | Configuration |
| --- | --- | --- |
| **NetworkManager** | Red Hat, Fedora, postes de travail | commande `nmcli`, fichiers dans `/etc/NetworkManager/` |
| **systemd-networkd** | serveurs minimaux, conteneurs | fichiers `.network` dans `/etc/systemd/network/` |
| **netplan** | Ubuntu | fichiers YAML dans `/etc/netplan/`, traduits pour l'un des deux précédents |
| **ifupdown** | Debian classique | le fichier `/etc/network/interfaces` |

Sur un serveur inconnu, on cherche d'abord **lequel est actif**, avec `systemctl is-active NetworkManager systemd-networkd`, avant de modifier quoi que ce soit : deux outils qui se disputent la même interface produisent des configurations qui changent sans raison apparente.

## adresse fixe ou DHCP

Le **DHCP** attribue l'adresse automatiquement : c'est la règle sur les postes de travail. Un **serveur** a presque toujours une adresse **fixe**, que d'autres machines, des règles de pare-feu et des enregistrements DNS désignent. On la pose dans la configuration permanente, avec quatre informations : l'adresse et son masque, la passerelle, et les serveurs DNS. Une alternative, courante dans les réseaux bien tenus, est une **réservation DHCP** : le serveur DHCP donne toujours la même adresse à la même carte, et la configuration reste centralisée.

Avec NetworkManager :

```bash
nmcli device status
sudo nmcli connection modify "Wired connection 1" \
  ipv4.method manual ipv4.addresses 192.0.2.10/24 \
  ipv4.gateway 192.0.2.1 ipv4.dns 192.0.2.53
sudo nmcli connection up "Wired connection 1"
```

`nmcli` enregistre la configuration, puis `connection up` l'applique. Sur un serveur distant, cette dernière commande coupe un instant le réseau : si l'adresse change, ta session SSH ne reviendra pas d'elle-même. On prévoit donc une console de secours, ou un retour en arrière automatique, comme le fait `netplan try` sur Ubuntu, qui annule la modification si on ne la confirme pas dans les deux minutes.

## IPv6 en bref

Une interface Linux porte presque toujours une adresse **IPv6**, même quand personne ne l'a configurée : l'adresse **de lien local**, qui commence par `fe80::`, fabriquée automatiquement et valable seulement sur le réseau local. Sur un réseau qui distribue IPv6, la machine reçoit en plus une adresse **globale**, souvent par l'**autoconfiguration** (*SLAAC*) : le routeur annonce le préfixe du réseau, et la machine compose elle-même la suite. Les commandes sont les mêmes, avec `-6` :

```bash
ip -6 addr show dev enp1s0
ip -6 route
sudo ip -6 addr add 2001:db8::10/64 dev enp1s0
```

Une conséquence de sécurité est souvent oubliée : un service qui écoute sur `[::]` est joignable en IPv6, et un pare-feu qui ne filtre qu'IPv4 le laisse grand ouvert. On configure les deux, ou l'on désactive IPv6 là où il ne sert pas.

## la configuration permanente, fichier par fichier

Sur Ubuntu, la même adresse fixe s'écrit dans un fichier de netplan, `/etc/netplan/50-serveur.yaml` :

```yaml
network:
  version: 2
  ethernets:
    enp1s0:
      addresses: [192.0.2.10/24]
      routes:
        - to: default
          via: 192.0.2.1
      nameservers:
        addresses: [192.0.2.53]
```

`sudo netplan try` l'applique, puis attend une confirmation. Sur une Debian classique, c'est un bloc de `/etc/network/interfaces`, appliqué par `sudo ifup enp1s0` :

```text
auto enp1s0
iface enp1s0 inet static
    address 192.0.2.10/24
    gateway 192.0.2.1
```

Les formats diffèrent, les informations restent les mêmes : l'adresse et son masque, la passerelle, les serveurs DNS. Le YAML de netplan est sensible à l'indentation : une espace de trop, et le fichier est refusé, d'où l'intérêt de `netplan try`, qui revient en arrière tout seul.

## démonstration : changer l'adresse d'un serveur distant

Un serveur hébergé doit passer de `192.0.2.143` à `192.0.2.10`, et l'on n'y accède que par SSH. La méthode prudente commence par **ajouter** la nouvelle adresse, sans retirer l'ancienne : `sudo ip addr add 192.0.2.10/24 dev enp1s0`. On ouvre ensuite une **seconde** session SSH vers la nouvelle adresse, depuis un autre terminal. Si elle fonctionne, on écrit la configuration permanente, on l'applique, et l'on vérifie qu'on se reconnecte. À aucun moment on n'a scié la branche sur laquelle on était assis. Si quelque chose tourne mal, la console de l'hébergeur reste le dernier recours : on vérifie qu'on sait l'ouvrir **avant** de commencer, pas pendant la panne.

## vérifier après chaque changement

Quelques commandes, toujours dans le même ordre, confirment qu'une configuration est bonne :

```bash
ip -br link                 # le lien est-il UP ?
ip -br addr                 # l'adresse est-elle la bonne, avec le bon masque ?
ip route                    # une route par défaut, une seule ?
ping -c 2 192.0.2.1         # la passerelle répond-elle ?
```

Deux routes par défaut, une adresse en `/32` au lieu de `/24`, une interface `DOWN` après un redémarrage : ces erreurs courantes se voient toutes ici. La leçon suivante prolonge cette vérification en une vraie méthode de diagnostic.

## à toi de jouer

Le Linux des exercices a une carte réseau, `eth0`, mais rien n'est configuré, et aucun câble n'est branché derrière. Configure-la à la main, comme sur un serveur qu'on installe :

1. regarde l'état des interfaces : `ip link`. Ni `lo` ni `eth0` n'ont `UP` entre leurs chevrons. Le `ip` de BusyBox ne connaît pas l'option `-br` : la sortie complète fera l'affaire ;
2. active les deux : `ip link set lo up`, puis `ip link set eth0 up` ;
3. donne une adresse à `eth0` : `ip addr add 192.0.2.10/24 dev eth0`, puis la route par défaut : `ip route add default via 192.0.2.1` ;
4. garde l'état obtenu : `ip addr show eth0 > adresses.txt`, puis `ip route > routes.txt` ;
5. demande au noyau par où partirait un paquet vers une adresse lointaine : `ip route get 198.51.100.7 > chemin.txt`, puis vers une adresse du réseau local : `ip route get 192.0.2.25` ;
6. enfin, essaie de joindre la passerelle : `ping -c 2 -W 1 192.0.2.1`.

## les pièges

- **Configurer avec `ip` et croire que c'est permanent.** Tout disparaît au redémarrage : il faut l'outil de la distribution.
- **Oublier le masque.** `192.0.2.10` sans `/24` devient un `/32` : plus aucun voisin n'est joignable directement.
- **Deux routes par défaut.** Le trafic part par l'une ou l'autre, au gré des métriques : une seule.
- **Deux gestionnaires de réseau sur la même interface.** La configuration change toute seule : `systemctl is-active` d'abord.
- **Changer l'adresse d'un serveur distant sans filet.** La session se perd : console de secours, ou `netplan try`.
- **Se fier aux noms `eth0`.** Ils peuvent changer d'ordre : les noms prévisibles comme `enp1s0` sont stables.

## à retenir

- Les interfaces : **`lo`**, la boucle locale, et des noms prévisibles comme **`enp1s0`**. État du lien : `UP`, `LOWER_UP`, `NO-CARRIER`.
- **`ip link set … up`**, **`ip addr add adresse/masque dev …`**, **`ip route add default via passerelle`** : temporaire.
- **`ip -br addr`**, **`ip route`**, **`ip route get`** pour voir et comprendre.
- Le permanent : **NetworkManager** (`nmcli`), **systemd-networkd**, **netplan**, **ifupdown** ; un seul actif à la fois.
- Un serveur a une adresse **fixe** : adresse et masque, passerelle, DNS.
- À distance, toujours un **filet** : console, ou retour en arrière automatique.
