Jusqu'ici, tes scripts recevaient leurs données par leurs arguments, dans un ordre fixe. C'est vite limitant : comment dire « garde trois fichiers au lieu de sept », « montre-moi ce que tu ferais sans le faire », ou « ne me demande pas confirmation » ? Les commandes que tu utilises tous les jours répondent avec des **options** : `ls -l`, `tar -cf`, `rm -i`. Cette leçon donne les mêmes manières à tes scripts. Elle montre aussi comment **poser une question** à l'utilisateur, et surtout quand ne pas le faire.

## objectifs

À la fin de cette leçon, tu sais :

- lire une saisie avec `read`, avec une invite, une valeur par défaut, une saisie masquée ou un délai ;
- demander une confirmation avant une action destructrice ;
- savoir si un terminal est là pour répondre, avec `[[ -t 0 ]]` ;
- accepter des options courtes avec `getopts`, avec ou sans valeur ;
- écrire une aide `-h`, valider les valeurs reçues et rendre le code 2 en cas de mauvaise utilisation.

## pourquoi ça compte

Un script d'administration est souvent destructeur : il supprime, écrase, redémarre. Les options lui donnent des **garde-fous** que tout le monde connaît : une simulation pour voir avant d'agir, une confirmation, une aide qui dit ce qu'il fait. Elles le rendent aussi **automatisable** : une tâche planifiée ne peut pas répondre à une question, il lui faut une option qui y réponde d'avance. Enfin, tout ce qu'un script lit de l'extérieur, saisie ou option, est une **entrée non fiable** : un nombre qui n'en est pas un, un chemin vide, un nom qui commence par un tiret. Valider ces entrées, c'est la première ligne de défense d'un script.

## read : poser une question

```bash
read -r -p "Nom du compte à créer : " compte
echo "Création de $compte..."
```

`read` lit une ligne sur l'entrée standard et la range dans la variable. `-p` affiche une invite, `-r` garde les barres obliques inverses telles quelles, comme dans les boucles de lecture. Les autres options utiles :

| Option | Effet |
| --- | --- |
| `-s` | saisie **masquée**, pour un mot de passe : rien ne s'affiche |
| `-t 10` | abandon après 10 secondes sans réponse : `read` échoue |
| `-n 1` | lit un seul caractère, sans attendre Entrée |
| `-a liste` | range les mots de la ligne dans un tableau |

Une **valeur par défaut** se donne avec un développement vu à la leçon sur les variables :

```bash
read -r -p "Dossier de destination [/srv/sauvegardes] : " dest
dest=${dest:-/srv/sauvegardes}
```

Et une réponse s'**accepte seulement si elle est valide**, en reposant la question au besoin :

```bash
until [[ $port =~ ^[0-9]+$ ]] && (( port >= 1 && port <= 65535 )); do
  read -r -p "Port d'écoute (1 à 65535) : " port
done
```

Pour un secret, `read -s` évite l'affichage, mais ne règle pas tout. La valeur reste dans une variable du script, visible dans une trace `bash -x`. Et transmise en argument à une commande, elle apparaîtrait dans la liste des processus, que tout utilisateur de la machine peut lire avec `ps`. Un secret se passe donc par l'entrée standard ou par un fichier aux droits restreints, jamais en argument : `mysql --defaults-extra-file=/root/.my.cnf` plutôt que `mysql -p"$motdepasse"`.

## demander confirmation

Avant une suppression, une question où la réponse prudente est la valeur par défaut :

```bash
read -r -p "Supprimer 42 fichiers ? [o/N] " reponse
case "$reponse" in
  [oO]*) ;;                      # o, O, oui, Oui : on continue
  *) echo "Annulé."; exit 1 ;;   # tout le reste, y compris Entrée seule
esac
```

Le `N` majuscule de `[o/N]` est une convention : il indique la réponse par défaut, ici **non**. Une simple pression sur Entrée annule. Pour une action vraiment grave, on demande de **retaper un nom** plutôt qu'un simple « o », comme le fait GitHub pour supprimer un dépôt : `read -r -p "Tape le nom du serveur pour confirmer : " nom`.

## un terminal est-il là ?

Un script lancé par une tâche planifiée, ou dont l'entrée vient d'un tube, n'a personne pour répondre. Un `read` y lit une ligne vide, ou la fin du fichier, et la confirmation échoue au mieux, ou au pire lit une donnée qui ne lui était pas destinée. Le test **`-t 0`** dit si l'entrée standard est un terminal :

```bash
if [[ ! -t 0 ]]; then
  echo "Pas de terminal pour confirmer : relance avec -y." >&2
  exit 2
fi
```

La règle qui en découle : **toute question doit pouvoir être évitée par une option**. Un script interactif seulement ne s'automatise pas.

## getopts : des options comme une vraie commande

`getopts`, une commande intégrée de bash, lit les options une par une. On l'appelle dans une boucle :

```bash
garder=7
simulation=non
while getopts ":n:sh" opt; do
  case "$opt" in
    n)  garder=$OPTARG ;;
    s)  simulation=oui ;;
    h)  usage; exit 0 ;;
    :)  echo "L'option -$OPTARG attend une valeur." >&2; exit 2 ;;
    \?) echo "Option inconnue : -$OPTARG" >&2; exit 2 ;;
  esac
done
shift $(( OPTIND - 1 ))
```

Tout se joue dans la chaîne **`":n:sh"`** :

- chaque lettre est une option acceptée : `-n`, `-s`, `-h` ;
- une lettre suivie de **`:`** attend une **valeur**, que `getopts` range dans **`OPTARG`** : `-n 3` donne `OPTARG=3` ;
- le **`:`** en tête rend `getopts` silencieux : c'est le script qui gère les erreurs, avec le cas `:` (valeur manquante) et le cas `?` (option inconnue), écrit `\?` dans le `case` pour qu'il ne soit pas pris pour un joker.

`getopts` accepte toutes les écritures habituelles : `-s -n 3`, `-sn 3`, `-n3`. Il s'arrête au premier argument qui n'est pas une option, ou à `--`. Après la boucle, **`OPTIND`** contient le numéro du premier argument restant, et **`shift $(( OPTIND - 1 ))`** retire les options déjà lues : `$1` redevient le premier argument « ordinaire », comme un nom de dossier.

`getopts` ne connaît que les options **courtes**, d'une lettre. Pour des options longues comme `--aide` ou `--garder=3`, on lit les arguments soi-même, comme le montre la section suivante, ou on utilise la commande `getopt` de util-linux, plus complète mais propre à Linux.

## les options longues, à la main

Les commandes GNU acceptent aussi des options longues, plus lisibles dans un script ou une crontab : `--garder 3`, `--simulation`, `--aide`. `getopts` ne les connaît pas, mais une boucle sur les arguments suffit :

```bash
while (( $# > 0 )); do
  case "$1" in
    -n|--garder)     garder=${2:?"$1 attend une valeur"}; shift ;;
    --garder=*)      garder=${1#*=} ;;
    -s|--simulation) simulation=oui ;;
    -h|--aide)       usage; exit 0 ;;
    --)              shift; break ;;
    -*)              echo "Option inconnue : $1" >&2; exit 2 ;;
    *)               break ;;
  esac
  shift
done
```

La boucle regarde le premier argument, le traite, puis `shift` le retire. Une option qui attend une valeur la prend dans `$2`, et fait un `shift` de plus pour la consommer. La forme `--garder=3` se découpe avec `${1#*=}`, qui retire tout jusqu'au signe égal. `--` arrête la lecture des options, et le premier argument qui ne commence pas par un tiret aussi : ce qui reste dans `"$@"` est la liste des arguments ordinaires. Ce style est plus long que `getopts`, mais il gère à la fois les formes courtes et longues. Il ne sait pas, en revanche, regrouper des options courtes : `-sn 3` n'y est pas compris.

## les réglages par l'environnement

Une troisième source de réglages complète les options : l'**environnement**. Une tâche planifiée ou un conteneur fixe volontiers ses réglages par des variables plutôt que par des options :

```bash
garder=${SAUVEGARDE_GARDER:-7}
destination=${SAUVEGARDE_DEST:-/srv/sauvegardes}
```

La valeur par défaut s'applique si la variable est absente ou vide. L'usage veut que l'**option l'emporte** sur l'environnement, qui l'emporte lui-même sur la valeur par défaut : on lit donc l'environnement d'abord, puis les options, qui écrasent ce qui précède. Documente ces variables dans l'aide, au même titre que les options, et donne-leur un préfixe propre au script, pour ne pas reprendre par accident une variable qui existe déjà. Une variable d'environnement n'est jamais plus fiable qu'une option : elle se **valide** de la même façon.

## lire un fichier ou l'entrée standard

Beaucoup de commandes lisent le fichier qu'on leur donne, ou leur entrée standard si on ne leur en donne pas : `grep motif fichier` comme `commande | grep motif`. Un script obtient le même comportement en une ligne :

```bash
while IFS= read -r ligne; do
  traiter "$ligne"
done < "${1:-/dev/stdin}"
```

Sans argument, `${1:-/dev/stdin}` vaut `/dev/stdin`, c'est-à-dire l'entrée standard : le script s'utilise aussi bien avec un fichier qu'au bout d'un tube. Par convention, un argument réduit à un tiret, `-`, désigne lui aussi l'entrée standard.

## l'aide, la validation et les conventions

Un script qui a des options doit dire lesquelles. Une fonction `usage` avec un here-document fait l'affaire :

```bash
usage() {
  cat << FIN
Usage : $(basename "$0") [-n NOMBRE] [-s] [-h] DOSSIER
  -n NOMBRE  nombre de fichiers à garder (défaut : 7)
  -s         simulation : affiche sans rien supprimer
  -h         affiche cette aide
FIN
}
```

Les conventions que tes utilisateurs attendent, parce que toutes les commandes les suivent :

- **`-h`** affiche l'aide et rend 0 ;
- une **mauvaise utilisation** (option inconnue, valeur manquante, argument absent) affiche l'aide sur `>&2` et rend **2** ;
- **`--`** marque la fin des options : `script.sh -- -fichier-bizarre` ;
- les valeurs reçues sont **validées** avant usage : `[[ $garder =~ ^[0-9]+$ ]]` pour un nombre, `[[ -d $dossier ]]` pour un dossier.

Une option qui reçoit `-n trois` doit être refusée net, et non transformée en zéro par un calcul qui, plus loin, supprimerait tout.

## à toi de jouer

Le dossier `journaux` contient dix journaux quotidiens, du 21 au 30 septembre. Leurs noms portent la date au format `AAAA-MM-JJ` : l'ordre alphabétique est donc l'ordre chronologique. `rotation.sh` garde les plus récents et supprime les autres. Pilote-le uniquement par ses options :

1. lis son aide : `bash rotation.sh -h` ;
2. simule une rotation qui garde trois journaux : `bash rotation.sh -s -n 3 journaux`. Sept fichiers sont listés, rien n'est supprimé ;
3. essaie une valeur invalide : `bash rotation.sh -n trois journaux`, puis `echo $?`. Le script refuse, avec le code 2 ;
4. lance la vraie rotation : `bash rotation.sh -n 3 journaux`. À la question, réponds simplement par Entrée : la réponse par défaut annule ;
5. relance la même commande, et réponds `o` cette fois. Vérifie avec `ls journaux`.

Lis le script avec `cat rotation.sh` : tu y retrouveras `getopts` et sa chaîne `":n:syh"`, la validation de `-n` par une expression régulière, le test `-t 0`, et la confirmation par `case`. ## les pièges

- **Un script qui pose des questions et rien d'autre.** Il ne s'automatise pas : chaque question doit avoir son option.
- **Un `read` sans terminal.** Dans une tâche planifiée ou après un tube, il lit du vide ou des données : teste `-t 0`.
- **Une confirmation dont la valeur par défaut est « oui ».** Une pression distraite sur Entrée supprime tout : `[o/N]`.
- **Oublier `shift $(( OPTIND - 1 ))`.** `$1` reste la première option au lieu de l'argument attendu.
- **Ne pas valider une valeur.** `-n trois` devient 0 dans un calcul, et le script supprime tout.
- **Écrire `?)` au lieu de `\?)` dans le `case`.** Non protégé, `?` est un joker qui attrape toutes les options d'une lettre.
- **Lire un mot de passe sans `-s`.** Il s'affiche à l'écran, et parfois dans l'historique ou une capture.

## à retenir

- **`read -r -p "Question : " var`** pour une saisie ; **`-s`** pour un secret, **`-t`** pour un délai, **`${var:-défaut}`** pour une valeur par défaut.
- Une confirmation **`[o/N]`** lue avec `case`, où Entrée seule annule.
- **`[[ -t 0 ]]`** : pas de terminal, pas de question. Chaque question a son **option**.
- **`while getopts ":n:sh" opt; do case ... esac; done`**, puis **`shift $(( OPTIND - 1 ))`** ; `:` après une lettre pour une valeur dans **`OPTARG`**.
- **`-h`** rend 0, une mauvaise utilisation rend **2** avec l'aide sur `>&2`, et toute valeur reçue est **validée**.
