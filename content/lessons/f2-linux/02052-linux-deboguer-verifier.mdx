Tout script finit un jour par donner un résultat faux. Le plus souvent, sans aucune erreur : il tourne, il se termine, et le nombre qu'il affiche est simplement incorrect. Relire le code ne suffit pas toujours, parce qu'on relit ce qu'on **croit** avoir écrit. Bash peut en revanche te montrer ce qu'il **fait vraiment**, commande par commande, avec les valeurs réelles des variables. Et un outil comme ShellCheck relit ton script avant même que tu le lances, avec l'œil de quelqu'un qui connaît tous les pièges de ce module.

## objectifs

À la fin de cette leçon, tu sais :

- exploiter un message d'erreur de bash et son numéro de ligne ;
- vérifier la syntaxe d'un script sans l'exécuter, avec `bash -n` ;
- suivre une exécution pas à pas avec `bash -x` et `set -x`, et rendre la trace lisible avec `PS4` ;
- ajouter des messages de débogage qu'une variable active ou coupe ;
- lire les avertissements de **ShellCheck**, et savoir quand en faire taire un ;
- tester un script avant de le confier à la production.

## pourquoi ça compte

Un bug dans un script d'administration se paie souvent en production : la sauvegarde incomplète, le compte créé avec les mauvais droits, la purge qui a supprimé un fichier de trop. Plus tôt on le trouve, moins il coûte. ShellCheck le trouve avant l'exécution, la trace le trouve à la première exécution, et les tests le trouvent avant la mise en service. Ces outils sont aussi ceux qu'on attend de toi en équipe : dans beaucoup d'entreprises, aucun script ne passe en revue de code sans un ShellCheck propre.

## lire le message d'erreur

Bash dit presque toujours où il s'est arrêté :

```text
./purge.sh: line 14: [: -gt: unary operator expected
./purge.sh: line 22: syntax error near unexpected token `fi'
./purge.sh: line 9: archive: unbound variable
```

Le nom du script, le **numéro de ligne**, puis le problème. Dans le premier cas, à la ligne 14, un `[` a reçu `-gt` sans rien devant : la variable à comparer était vide, et sans guillemets. Le deuxième est une erreur de **syntaxe** : bash a trouvé un `fi` qu'il n'attendait pas, souvent à cause d'un `then` oublié ou d'un `;` manquant un peu plus haut. Le troisième vient de `set -u` : la variable `archive` n'a jamais été définie, souvent une faute de frappe. Commence toujours par **ouvrir le script à la ligne indiquée** : `vi +14 purge.sh` y place directement le curseur.

## bash -n : vérifier la syntaxe

```bash
bash -n purge.sh
```

`-n` lit le script et vérifie sa syntaxe **sans rien exécuter** : un `if` sans `fi`, une guillemet non fermée, une accolade en trop. S'il ne dit rien, la syntaxe est bonne, ce qui ne prouve pas que le script soit juste. C'est un contrôle sans risque, à faire avant toute exécution d'un script qu'on vient de modifier, surtout sur un serveur.

## bash -x : voir ce qui s'exécute

L'option **`-x`** (*xtrace*) affiche chaque commande **juste avant de l'exécuter**, après tous les développements, précédée d'un `+` :

```bash
bash -x purge.sh /var/log/app
```

```text
+ dossier=/var/log/app
+ garder=7
++ ls /var/log/app
++ wc -l
+ nombre=3
+ '[' 3 -gt 7 ']'
+ echo 'Rien à purger.'
Rien à purger.
```

On y voit les **vraies valeurs** : ce que valait `nombre`, ce que le `[` a vraiment comparé. Le `++` signale une commande exécutée dans une substitution `$( )`, un niveau plus bas. C'est le meilleur outil pour comprendre un résultat faux : la ligne où la valeur cesse d'être celle que tu attendais désigne le bug.

La trace s'écrit sur la **sortie d'erreur**. Pour l'enregistrer à part : `bash -x script.sh 2> trace.txt`. Pour ne tracer qu'une partie d'un long script, on encadre la zone suspecte :

```bash
set -x     # début de la trace
calculer_retention
purger_anciennes
set +x     # fin de la trace
```

La variable **`PS4`** définit le préfixe des lignes de trace. Avec le nom du fichier et le numéro de ligne, la trace devient une carte du script :

```bash
export PS4='+ ${BASH_SOURCE##*/}:${LINENO}: '
bash -x purge.sh /var/log/app
```

```text
+ purge.sh:5: dossier=/var/log/app
+ purge.sh:6: garder=7
```

Attention : la trace affiche **tout**, y compris les mots de passe et les jetons que le script manipule. Ne colle jamais une trace dans un ticket ou un canal de discussion sans la relire.

## des messages de débogage à la demande

Pour un script qu'on maintient longtemps, on prévoit des messages de débogage, éteints par défaut, qu'une variable d'environnement allume :

```bash
debug() {
  [[ ${DEBUG:-0} == 1 ]] && echo "DEBUG : $*" >&2
  return 0
}

debug "fichiers trouvés : ${#fichiers[@]}"
```

`DEBUG=1 ./purge.sh /var/log/app` affiche les messages, `./purge.sh /var/log/app` reste muet. Le `return 0` final évite que la fonction rende l'échec du test quand le débogage est coupé, ce qui arrêterait un script en `set -e`. Et pour voir exactement ce que contient une variable, l'astuce de la leçon sur les variables reste la meilleure : `printf '[%s]\n' "$var"`.

## ShellCheck : un relecteur automatique

**ShellCheck** analyse un script sans l'exécuter et signale les erreurs et les pièges connus : variables sans guillemets, `cd` non vérifié, `for` sur la sortie de `ls`, comparaison de nombres avec `>`, variable jamais utilisée, et des centaines d'autres. Il s'installe depuis les dépôts : `sudo apt install shellcheck`.

```bash
shellcheck purge.sh
```

Chaque avertissement indique la ligne, souligne la partie en cause, donne un **code** comme `SC2086` et un niveau de gravité : `error`, `warning`, `info` ou `style`. Chaque code a sa page explicative sur le wiki du projet, avec le problème, un exemple et la correction : `https://www.shellcheck.net/wiki/SC2086`. Ce wiki est l'un des meilleurs cours de bash qui existent.

Les codes que tu croiseras le plus, et que ce module t'a appris à éviter :

| Code | Problème |
| --- | --- |
| `SC2086` | variable sans guillemets : découpage en mots et jokers |
| `SC2164` | `cd` sans `\|\| exit` : le script continue dans le mauvais dossier |
| `SC2045` | `for f in $(ls ...)` : itérer sur la sortie de `ls` est fragile |
| `SC2155` | `local x=$(...)` ou `export x=$(...)` : le code de retour est masqué |
| `SC2034` | variable affectée mais jamais utilisée, souvent une faute de frappe |
| `SC2181` | `if [ $? -eq 0 ]` : tester la commande directement est plus sûr |

Quand un avertissement ne s'applique pas, parce que le découpage en mots est voulu par exemple, on le fait taire **sur une seule ligne**, avec la raison :

```bash
# shellcheck disable=SC2086  # $OPTIONS contient plusieurs options, à découper volontairement
rsync $OPTIONS "$source" "$dest"
```

ShellCheck s'intègre aux éditeurs (VS Code, vim, Emacs), qui soulignent les problèmes pendant la frappe, et à la chaîne d'intégration continue, où il bloque un script fautif avant sa fusion. Son compagnon **`shfmt`** remet en forme un script, comme un formateur de code.

En équipe, on ne compte pas sur la bonne volonté de chacun : ShellCheck tourne dans la **chaîne d'intégration continue**, sur chaque modification proposée, et une erreur bloque la fusion. Quelques lignes suffisent, par exemple dans GitHub Actions :

```yaml
- name: ShellCheck
  run: shellcheck --severity=warning scripts/*.sh
```

Le niveau `warning` laisse passer les simples remarques de style, et arrête tout ce qui ressemble à un vrai bug. Chaque script ajouté au dépôt est ainsi relu automatiquement, avant même qu'un collègue ne le lise.

## tester avant la production

Un script se teste comme un programme :

- sur des **cas variés** : sans argument, avec un fichier absent, un nom à espace, un dossier vide, beaucoup de fichiers. Le banc de tests de la leçon sur les conditions en était un exemple ;
- dans un **environnement jetable** : un dossier de test, une machine virtuelle, un conteneur, jamais la production directement ;
- avec une **simulation** quand il en a une : l'option `-s` de la leçon précédente.

Pour aller plus loin, **bats-core** est un cadre de tests automatiques pour bash : chaque test lance le script et vérifie sa sortie et son code de retour. Le bilan de ce module te fera écrire un script qui passe une série de tests de ce genre.

Ensuite, un vrai bug, sans aucune erreur. `stats.sh` compte les réponses 404 d'un journal d'accès, dont chaque ligne contient une adresse IP, une date, un code HTTP et une taille. Il affiche `404 : 0`. Pourtant, il y en a.

1. vérifie : `bash stats.sh acces.log`, puis `grep -c ' 404 ' acces.log` ;
2. la syntaxe est-elle en cause ? `bash -n stats.sh` ne dit rien : elle est correcte ;
3. trace l'exécution dans un fichier : `bash -x stats.sh acces.log 2> trace.txt`, puis lis le début : `head -12 trace.txt`. Regarde ce que le `[[` compare vraiment ;
4. tu as trouvé : la dernière variable de `read` reçoit **tout le reste de la ligne**. Ajoute une variable pour le dernier champ : `sed -i 's/read -r ip date code;/read -r ip date code taille;/' stats.sh` ;
5. relance et garde le résultat : `bash stats.sh acces.log > resultat.txt`.

## les pièges

- **Ignorer le numéro de ligne d'une erreur.** Il dit où regarder ; une erreur de syntaxe se situe souvent juste au-dessus.
- **Croire qu'un `bash -n` silencieux prouve que le script est juste.** Il ne vérifie que la syntaxe.
- **Chercher la trace dans la sortie standard.** Elle va sur la sortie d'erreur : `2> trace.txt`.
- **Partager une trace sans la relire.** Elle contient les valeurs réelles, mots de passe compris.
- **Faire taire ShellCheck pour tout le fichier.** On désactive un code sur une ligne, avec la raison.
- **Tester directement en production.** Un dossier de test, une machine virtuelle, ou une simulation d'abord.

## à retenir

- Un message d'erreur donne **la ligne** : commence par là, et regarde juste au-dessus pour une erreur de syntaxe.
- **`bash -n`** vérifie la syntaxe sans exécuter ; **`bash -x`** (ou **`set -x`** … **`set +x`**) montre chaque commande avec ses vraies valeurs, sur la sortie d'erreur.
- **`PS4='+ ${BASH_SOURCE##*/}:${LINENO}: '`** rend la trace lisible ; une trace se relit avant d'être partagée.
- Des messages **`DEBUG`** activés par une variable d'environnement, sur `>&2`.
- **ShellCheck** avant chaque mise en service : un code `SCxxxx` par problème, expliqué sur son wiki ; on ne le fait taire que ligne par ligne, avec la raison.
- On **teste** sur des cas variés, dans un environnement jetable, jamais d'abord en production.
