La leçon précédente a expliqué comment fonctionnent les paquets. Place à la pratique : trouver le bon paquet parmi des dizaines de milliers, l'installer sans embarquer la moitié du dépôt, le retirer proprement, et savoir, des semaines plus tard, **qui** a installé **quoi** et **quand**. Ces gestes reviennent chaque jour dans la vie d'un administrateur. La dernière question, elle, revient dans chaque enquête de sécurité : le journal des installations est l'un des premiers fichiers qu'on lit sur une machine suspecte.

## objectifs

À la fin de cette leçon, tu sais :

- chercher un paquet par son nom ou sa description, et lire sa fiche ;
- installer un paquet, avec ou sans ses recommandations, dans une version précise ou depuis un fichier `.deb` ;
- retirer un paquet avec `remove` ou `purge`, et comprendre la différence ;
- nettoyer les dépendances devenues inutiles avec `autoremove` ;
- marquer un paquet comme installé à la main, automatique ou bloqué avec `apt-mark` ;
- retrouver dans les journaux ce qui a été installé ou retiré, quand et par qui ;
- transposer ces commandes avec `dnf`.

## pourquoi ça compte

Chaque paquet installé est du code qui tourne, ou peut tourner, sur ta machine. Chaque paquet inutile est donc une **surface d'attaque** en plus : un service qui écoute sans raison, une bibliothèque qui peut contenir une faille, un outil qu'un attaquant sera content de trouver déjà installé. Les guides de durcissement, comme celui de l'ANSSI, recommandent tous le **minimalisme** : n'installer que le nécessaire, retirer ce qui ne sert plus. À l'inverse, le journal des installations est une mine pour l'enquêteur : un attaquant qui a obtenu les droits de root installe souvent ses outils avec le gestionnaire de paquets, parce que c'est simple, et laisse ainsi une trace datée.

## chercher et décrire

```bash
apt search "web server"        # dans les noms et les descriptions
apt search --names-only nginx  # dans les noms seulement
apt show nginx                 # la fiche complète du paquet
apt-cache policy nginx         # la version installée, les versions disponibles, et leurs dépôts
```

`apt search` ratisse large : chercher `python` renvoie des milliers de résultats. `--names-only` resserre la recherche, et un filtre `grep` fait le reste. `apt show` affiche la fiche vue à la leçon précédente : version, dépendances, taille, dépôt d'origine. `apt-cache policy` répond à une question fréquente : quelle version est installée (`Installed`), laquelle serait installée (`Candidate`), et depuis quel dépôt. On y revient à la leçon sur les dépôts.

Pour savoir quel paquet fournit une commande qui n'est **pas** encore installée, l'outil `apt-file` cherche dans le contenu de tous les paquets du dépôt : `apt-file search bin/dig` répond `bind9-dnsutils`. Sur Ubuntu, le shell le suggère d'ailleurs de lui-même quand on tape une commande introuvable.

## installer

```bash
sudo apt install nginx                          # le paquet et ses dépendances
sudo apt install -y nginx curl                  # plusieurs paquets, sans demander de confirmation
sudo apt install --no-install-recommends nginx  # sans les paquets simplement recommandés
sudo apt install nginx=1.22.1-9                 # une version précise
sudo apt install ./outil_2.1.0_amd64.deb        # un fichier .deb local, dépendances comprises
```

Avant d'installer, `apt` affiche la liste de ce qu'il va ajouter et l'espace disque nécessaire, puis demande confirmation. **Lis cette liste** : c'est là qu'on découvre qu'un petit outil tire derrière lui un environnement graphique complet. L'option `--no-install-recommends` évite souvent ce genre de surprise sur un serveur ; c'est d'ailleurs le réglage habituel des images de conteneurs, pour rester légères.

L'option `-y` répond oui d'avance. Elle est indispensable dans un script, où personne n'est là pour répondre, mais dangereuse à la main : on valide sans lire. Pour un fichier `.deb` téléchargé, préfère `apt install ./fichier.deb` (le `./` est obligatoire, sinon `apt` cherche un paquet de ce nom dans les dépôts) à `dpkg -i`, qui n'installe pas les dépendances manquantes.

Une installation met à jour la base des paquets, et, pour un service, l'active souvent au passage : sur Debian, installer `nginx` le **démarre** aussitôt. C'est pratique, mais cela veut dire qu'un port s'ouvre dès l'installation, avant que tu aies relu la configuration. Un point à garder en tête sur un serveur exposé.

## retirer : remove, purge, autoremove

```bash
sudo apt remove nginx       # retire le logiciel, garde sa configuration dans /etc
sudo apt purge nginx        # retire le logiciel ET sa configuration
sudo apt autoremove         # retire les dépendances qui ne servent plus à rien
```

`remove` laisse la configuration en place, pour le cas où tu réinstallerais : le paquet apparaît alors en état **`rc`** dans `dpkg -l` (*removed, config-files*). `purge` efface aussi les fichiers de configuration du paquet. Attention : ni l'un ni l'autre ne touche aux **données** (un site dans `/var/www`, une base dans `/var/lib/postgresql`), ni aux fichiers que tu as créés toi-même. Pour retrouver les paquets retirés dont il reste la configuration : `dpkg -l | grep '^rc'`.

Quand tu installes `nginx`, `apt` installe aussi ses dépendances et les **marque automatiques** : elles ne sont là que pour lui. Quand `nginx` part, elles deviennent **orphelines**. `apt autoremove` les repère et propose de les retirer. Lis sa liste avant de valider : il arrive qu'un paquet que tu utilises directement ait été installé comme dépendance, et le voir partir surprend.

## apt-mark : manuel, automatique, bloqué

`apt` distingue les paquets installés **à la main** de ceux installés **comme dépendance**. `apt-mark` lit et modifie cette marque :

```bash
apt-mark showmanual            # ce qui a été installé à la main
sudo apt-mark manual libssl3   # je l'utilise directement : autoremove ne doit pas le retirer
sudo apt-mark hold nginx       # bloquer nginx dans sa version actuelle
apt-mark showhold              # la liste des paquets bloqués
sudo apt-mark unhold nginx     # le débloquer
```

`hold` bloque un paquet dans sa version : les mises à jour le laissent de côté. C'est utile pour éviter qu'une mise à jour casse une application qui dépend d'une version précise, mais c'est aussi une **dette** : un paquet bloqué ne reçoit plus ses **correctifs de sécurité**. Un blocage doit donc être temporaire, documenté, et relu régulièrement avec `apt-mark showhold`.

## lister

```bash
apt list --installed           # tout ce qui est installé
apt list --upgradable          # ce qui a une version plus récente disponible
dpkg -l                        # la même base, vue par dpkg, avec l'état de chaque paquet
```

`apt list --installed | wc -l` donne un ordre de grandeur : quelques centaines de paquets pour un serveur minimal, plusieurs milliers pour un poste de travail. Rappelle-toi qu'`apt` prévient lui-même que son affichage n'est pas stable : dans un script, on préfère `dpkg-query -W`, dont le format se choisit et ne change pas.

## vérifier et réinstaller

La base des paquets conserve l'empreinte de chaque fichier installé. `dpkg --verify` (ou `dpkg -V`) la compare aux fichiers présents sur le disque, et ne signale que ceux qui ont changé : `dpkg -V openssh-server` ne répond rien si tout est intact, et affiche une ligne commençant par `??5` pour un fichier dont le contenu diffère. Une configuration que tu as modifiée apparaîtra, c'est normal, avec un `c` qui la désigne comme fichier de configuration. Un **exécutable** modifié, en revanche, n'a aucune raison de l'être : c'est l'un des signes les plus nets d'une compromission. L'outil `debsums` fait le même travail, paquet par paquet. Côté Red Hat, c'est `rpm -V`.

Si un fichier a été abîmé ou supprimé par erreur, `sudo apt reinstall paquet` réinstalle la version d'origine, sans toucher à ta configuration. Sur une machine compromise, en revanche, on ne répare pas : on reconstruit, parce qu'on ne sait jamais tout ce que l'attaquant a modifié.

## l'historique : qui a installé quoi, et quand

Chaque opération d'`apt` est consignée dans **`/var/log/apt/history.log`** : la date de début et de fin, la ligne de commande exacte, l'utilisateur qui l'a lancée via `sudo`, et la liste des paquets installés, mis à jour ou retirés. Le détail de ce que `dpkg` a fait, paquet par paquet, est dans **`/var/log/dpkg.log`**. Ces fichiers tournent comme les autres journaux : les anciens sont compressés en `history.log.1.gz`, qu'on lit avec `zcat` ou `zgrep`.

Pour l'enquêteur, ces journaux répondent à trois questions : **quoi** (quels paquets), **quand** (à la seconde près) et **par qui** (la ligne `Requested-By`). Un outil réseau comme `socat` ou `ncat` installé en pleine nuit, ou un outil de journalisation comme `auditd` retiré juste avant, raconte une histoire à lui seul. Un attaquant averti effacera ces lignes, bien sûr, mais il ne pense pas toujours à tout, et leur absence soudaine est elle-même un indice.

## et avec dnf

| Besoin | apt | dnf |
|---|---|---|
| chercher | `apt search mot` | `dnf search mot` |
| décrire | `apt show paquet` | `dnf info paquet` |
| installer | `apt install paquet` | `dnf install paquet` |
| retirer | `apt remove` ou `apt purge` | `dnf remove paquet` |
| dépendances orphelines | `apt autoremove` | `dnf autoremove` |
| quel paquet fournit une commande | `apt-file search bin/dig` | `dnf provides '*/bin/dig'` |
| historique | `/var/log/apt/history.log` | `dnf history`, puis `dnf history info N` |

`dnf` va plus loin sur un point : `dnf history undo N` annule une opération passée, en retirant ce qu'elle avait installé. Il ne garde pas de configuration en état `rc` : un `remove` laisse seulement les fichiers de configuration modifiés, renommés en `.rpmsave`.

## les pièges

- **Valider sans lire la liste d'`apt`.** C'est là qu'on voit arriver des dizaines de paquets inattendus, ou partir un paquet utile.
- **Croire que `remove` efface tout.** La configuration reste, en état `rc` ; `purge` l'efface. Les données ne sont effacées par aucun des deux.
- **Lancer `autoremove` les yeux fermés.** Un paquet utilisé directement mais marqué automatique peut disparaître : `apt-mark manual` le protège.
- **Oublier un `hold`.** Un paquet bloqué ne reçoit plus de correctifs de sécurité.
- **Utiliser `dpkg -i` pour un `.deb` téléchargé.** Il n'installe pas les dépendances : `apt install ./fichier.deb`.
- **Installer un service sans penser qu'il démarre aussitôt.** Sur Debian, un port peut s'ouvrir avant que la configuration soit relue.

## à retenir

- Chercher : **`apt search`** (`--names-only`), décrire : **`apt show`**, versions et origine : **`apt-cache policy`**.
- Installer : **`apt install`**, avec **`--no-install-recommends`** sur un serveur, **`paquet=version`** pour une version, **`./fichier.deb`** pour un fichier local. Lis toujours la liste avant de valider.
- Retirer : **`remove`** garde la configuration (état `rc`), **`purge`** l'efface, **`autoremove`** nettoie les orphelins.
- **`apt-mark`** : `manual`, `auto`, `hold` (temporaire, car sans correctifs), `showhold`.
- Historique : **`/var/log/apt/history.log`** (quoi, quand, par qui) et **`/var/log/dpkg.log`**. Avec dnf : **`dnf history`**.
